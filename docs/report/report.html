1. Architecture, testing problems & tool choice

1. Application under test

Conduit (RealWorld example app) — a Medium-style blogging platform. Source: https://github.com/TonyMckes/conduit-realworld-example-app (MIT licence).

LayerTechnologyResponsibility
Web UIReact 19 + React Router 7 (HashRouter), Vite dev server on :3000Pages: Home, Login, Register, Settings, Editor, Article, Profile. Session kept in localStorage["loggedUser"] and React AuthContext.
HTTP clientAxios (frontend/src/services/*)Calls /api/*; Vite proxies /api to the backend.
Application serverNode.js + Express 5 on :3001REST API (/api/users, /api/user, /api/articles, /api/profiles, /api/tags).
AuthJWT (jsonwebtoken) + bcrypt password hashingverifyToken middleware reads Authorization: Token <jwt>.
Data accessSequelize 6 ORMModels: User, Article, Comment, Tag; join tables Favorites, Followers, TagList.
DatabasePostgreSQL 18Persistent storage.

Data flow for a typical write (e.g. publish article): UI form → Axios POST /api/articles with Authorization: Token … → verifyToken decodes the JWT and loads the user → controller validates fields → Sequelize INSERT into Articles/TagList → 201 JSON → UI navigates to /article/:slug.

2. Testing problems considered

  1. End-to-end critical workflows touching the database. These cover registration, login, logout, and creating, editing and deleting articles, plus comments, profile updates, favourites and follows. Every positive test reads the record back through the API, which proves the database was updated, not just that the UI changed.
  2. Unauthorized access. We send requests with no token, a forged token and a tampered token, and we try to edit or delete another user's article. We also check that protected pages and controls are hidden when there is no session.
  3. Form validation. We test native HTML5 required checks, server-side validation when the client checks are bypassed, invalid emails, duplicate emails, and missing or whitespace-only fields.
  4. Network failures. We abort requests, return mocked HTTP 500 responses, and set the browser context offline.
  5. Edge cases. We send very long titles, Unicode and special characters, and script/HTML injection (XSS).
  6. Cross-browser behaviour. Every test runs on Chromium, Firefox and WebKit (Safari engine).

3. Client-side testing technique used

Both techniques named in the brief are applied:

  • Session-data technique. injectSession() writes a session object straight into localStorage via page.addInitScript, before any app code runs. It uses the same shape the app itself stores. With it we can:
  • log in instantly as any user;
  • inject forged or tampered tokens (TC07, TC20);
  • delete the session mid-use (TC19);
  • start with no session at all (TC18).
  • Bypass technique. The client-side checks are switched off: page.evaluate() removes the required attributes and sets form.noValidate (TC17), or the payload is sent directly with APIRequestContext (TC13, TC25, TC29). This tests whether the server enforces the rules.
  • Network-layer manipulation. page.route() aborts or fulfils requests with mocked responses (TC09, TC24), and context.setOffline(true) simulates an offline client (TC26).

4. Choice of tool: Playwright

NeedWhy Playwright
Cross-browserOne API drives Chromium, Firefox and WebKit; configured as 3 projects in playwright.config.js.
Network failure simulationBuilt-in page.route() (abort/fulfill) and context.setOffline(); no proxy needed.
Session manipulationaddInitScript, page.evaluate, isolated browser contexts per test.
API + DB verification in the same testrequest fixture (APIRequestContext) replaces a separate Postman collection.
ReliabilityAuto-waiting locators and web-first assertions (toBeVisible, toHaveURL) reduce flakiness.
Evidence for bug reportsScreenshot, video and trace captured automatically on failure; HTML, JSON and JUnit reporters.
App lifecyclewebServer option starts frontend + backend before the run.

Selenium would need separate driver binaries and a proxy for network mocking. Cypress has limited WebKit support and cannot use several tabs or origins as freely. No AI agents or agentic test frameworks are used: all tests are hand-written Playwright Test scripts.

BUG-001: Failed article publish silently navigates to /article/undefined

FieldValue
Severity / PriorityMedium / High
Found byTC09 (network failure, page.route(...).abort())
PreconditionsLogged-in user on #/editor
Steps1. Fill in title, description and body. 2. Make POST /api/articles fail at the network level. 3. Click Publish Article.
ExpectedAn error message is shown. The user stays on the editor with the form data intact, and nothing is created.
ActualNo error message (.error-messages not found). The app navigates to #/article/undefined, which renders 404 Not Found, and the user's draft is lost.
Root causefrontend/src/helpers/errorHandler.js only console.logs errors that have no response, so it does not rethrow them. setArticle() therefore resolves to undefined, and ArticleEditorForm navigates to /article/${undefined}.
Evidencedocs/evidence/BUG-001_TC09_publish_network_failure.png, docs/evidence/BUG-001_TC09_video.webm
Suggested fixRethrow non-HTTP errors (e.g. throw "Network error, please retry") and only navigate when slug is truthy.
StatusOpen

BUG-002: Malformed e-mail addresses are accepted at registration

FieldValue
Severity / PriorityMedium / Medium
Found byTC13 (bypass technique: request sent directly to the API, skipping the browser's type="email" check)
StepsPOST /api/users with {"user":{"username":"u1","email":"not-an-email-u1","password":"TestPassword123!"}}
Expected422 with an "invalid email" message
Actual201 Created. The user is stored with the invalid e-mail and receives a token.
Root causeThe server does no format validation: email: DataTypes.STRING in backend/models/User.js has no isEmail validator, and the controller only checks presence and uniqueness.
Suggested fixAdd validate: { isEmail: true } to the Sequelize email attribute, and map SequelizeValidationError to 422.

BUG-003: Invalid or tampered JWT returns 500 Internal Server Error instead of 401

FieldValue
Severity / PriorityMedium / High
Found byTC07 (session-data technique: forged token injected into localStorage), TC20 (tampered signature)
Steps1. Put {"isAuth":true,"headers":{"Authorization":"Token invalid_test_token"},...} in localStorage.loggedUser. 2. Open #/editor and publish. Or: PUT/DELETE /api/articles/:slug or GET /api/user with a token whose last 3 characters are altered.
Expected401 Unauthorized
Actual500 for POST, PUT, DELETE and GET /user. Nothing is written to the database (data integrity holds), but the status code is wrong. Monitoring would see server faults instead of auth failures, and clients cannot tell "please log in again" apart from "server broken".
Root causeIn backend/middleware/authentication.js, jwt.verify throws JsonWebTokenError. The error middleware doesn't recognise this type, so errorHandler maps it to 500.
Evidencedocs/evidence/BUG-003_TC07_invalid_token.png
Suggested fixCatch JsonWebTokenError / TokenExpiredError in verifyToken and throw UnauthorizedError.
StatusOpen

BUG-004: Article title longer than 255 characters returns 500

FieldValue
Severity / PriorityLow / Medium
Found byTC27 (boundary value)
StepsPOST /api/articles with a valid token and title = 5000 × "A"
Expected422 with a "title too long" message
Actual500. PostgreSQL raises value too long for type character varying(255). The editor input has no maxlength, so a user can trigger this from the UI too.
Root causetitle and slug are DataTypes.STRING (VARCHAR 255), and neither the client nor the server checks the length.
Suggested fixAdd maxlength="255" in the editor, and a len: [1,255] validator returning 422 on the server.
StatusOpen

BUG-005: Whitespace-only title returns 500 and leaves an orphan article in the database

FieldValue
Severity / PriorityHigh / High (data integrity)
Found byTC29 (edge case, bypass technique)
Steps1. POST /api/articles with title: " ". 2. Repeat with any user.
Expected422 "A title is required"; nothing stored.
ActualFirst request: 500, yet a row is inserted into Articles with slug = '', title = ' ' and userId = NULL. Every later whitespace title (from any user) then gets 422 "Title already exists", a misleading message caused by the orphan row.
DB evidenceSELECT id, slug, title, "userId" FROM "Articles" WHERE trim(title)=''; returned a row with slug '', title ' ' and userId NULL
Root causeif (!title) treats " " as present. slugify() trims it to ''. Article.create succeeds, then a later step fails, and because there is no transaction nothing is rolled back. setAuthor is never reached.
Suggested fixValidate title.trim(), and wrap the whole create in sequelize.transaction().
StatusOpen

BUG-006: Unexpected server error on login crashes the whole app (blank screen)

FieldValue
Severity / PriorityHigh / High
Found byTC24 (network technique: page.route fulfils POST /api/users/login with HTTP 500 and body {"errors":{"server":["boom"]}}, as a proxy/gateway might)
Steps1. Open #/login. 2. Enter valid credentials. 3. Server/gateway answers 500 with a body that is not {errors:{body:[...]}}.
ExpectedStay on login and show "Something went wrong, please try again".
ActualThe page turns completely blank (React tree unmounted) and no error is shown. The user is not logged in, but the app is unusable until a manual reload.
Root causeerrorHandler.js does throw data.errors.body[0] without checking that body exists. The resulting TypeError object is passed to setErrorMessage, and rendering an Error object as a React child crashes the tree (browser console: Objects are not valid as a React child (found: [object Error])). There is no error boundary.
Evidencedocs/evidence/BUG-006_TC24_login_500_blank_screen.png
Suggested fixUse a defensive message such as data?.errors?.body?.[0] ?? "Unexpected error", and add a React error boundary.
StatusOpen

BUG-007: Logging in while offline navigates away from login and crashes the app

FieldValue
Severity / PriorityHigh / Medium
Found byTC26 (network technique: context.setOffline(true))
Steps1. Open #/login and fill in valid credentials. 2. Lose network connectivity. 3. Click Login.
ExpectedStay on #/login with a "network error" message; no session created.
ActualThe URL changes to #/ and the screen goes blank. No session is stored (security holds), but the user gets no feedback and the app is broken until a reload.
Root causeSame as BUG-001: the network error is swallowed, so userLogin() resolves undefined. LoginForm then calls setAuthState(undefined) and navigate("/"), and the components reading the auth state crash (browser console: Cannot read properties of undefined (reading 'headers')).

BUG-008: Race condition: concurrent articles with the same new tag fail and leave orphan rows

FieldValue
Severity / PriorityHigh / High (data integrity, real multi-user scenario)
Found byTC31 (5 rounds × 10 parallel POST /api/articles over separate connections, all introducing one new tag). It was first noticed as an intermittent 500 in TC06 setup during parallel test runs.
StepsSend ≥2 simultaneous create requests whose tagList contains a tag that does not exist yet.
ExpectedAll return 201; each article is stored with its author and the tag.
ActualTypically 3–9 of 10 requests return 500 "Validation error". The failed articles are still inserted, but without author or tags (orphans). Server log: SequelizeUniqueConstraintError: duplicate key value violates unique constraint "Tags_pkey".
Root causeA check-then-insert race: Tag.findByPk(tag) and then Tag.create(...), with no transaction and no findOrCreate.
Suggested fixUse Tag.findOrCreate (or INSERT ... ON CONFLICT DO NOTHING), and do the whole create inside sequelize.transaction().
StatusOpen

Non-defect observations

  • Cross-site scripting (XSS): TC28 injected a script tag into an article body. <script> and onerror payloads are not executed in any browser, so the app is safe here.
  • Cross-user authorization: TC22 tried to edit and delete another user's article and got 403 as expected. TC23 confirmed the edit and delete controls are hidden from non-authors. Authorization is correct.
  • Flaky test observation: in one of three full runs, TC17 timed out (30 s) on WebKit. It passed 10/10 when re-run alone. The cause was cold browser start while Vite re-optimised dependencies under 4 parallel workers. This is an environment effect, not an application defect.
  • Test-design lesson: in the first execution, TC13 and TC29 passed on Firefox and WebKit for the wrong reason. The defect inserted a record (BUG-002/BUG-005), so the next browser's identical request got a "duplicate" 422. The tests now use unique data and check the error message, not just the status code.
  • Environment issue (fixed): the root npm run dev script used single quotes, which cmd.exe on Windows does not understand, so the app would not start. Changed to escaped double quotes so it works on all OSes.

3. Cross-browser compatibility

All 31 test cases produced identical outcomes on Chromium, Firefox and WebKit. No browser-specific defects were found. Every defect lives in shared application logic (React error handling, Express/Sequelize validation, missing DB transactions), not in browser-dependent rendering.

4. Stability

  • Determinism. Every run starts from a freshly created database. Each test creates its own uniquely named users, articles and tags, so tests are independent and parallel-safe.
  • TC31 (race condition). Repeated 10× per browser in isolation, it detected the defect 30/30 times.
  • One flaky observation. During an earlier full run, TC17 timed out once on WebKit; it then passed 10/10 when re-run alone. It is attributed to cold browser start while Vite re-optimised dependencies, and it did not recur in the final runs.

5. Repository, installation & execution

Repository: https://github.com/harjotsingh-debug/conduit-e2e-testing. It contains the application source (backend/, frontend/), the tests (tests/e2e/), the configuration (playwright.config.js), these documents (docs/) and the raw results (reports/default, reports/bugs).

Application under test: RealWorld "Conduit": React (Vite) + Express + Sequelize + PostgreSQL. Tool: Playwright Test (UI + API testing on Chromium, Firefox and WebKit). No AI agents or agentic frameworks are used.

Prerequisites

  • Node.js >= 18.11 (tested on 22.x), npm, Git
  • PostgreSQL running locally (tested on 18)

Setup

git clone https://github.com/harjotsingh-debug/conduit-e2e-testing.git
cd conduit-e2e-testing
npm install
npx playwright install                     # downloads Chromium, Firefox, WebKit

# Database: create a login role once (as the postgres superuser)
psql -U postgres -c "CREATE ROLE conduit_user LOGIN CREATEDB PASSWORD 'conduit_local_pw';"

# Backend env file
cp backend/.env.example backend/.env

Edit backend/.env:

PORT=3001
JWT_KEY=any_long_random_string
DEV_DB_USERNAME=conduit_user
DEV_DB_PASSWORD=conduit_local_pw
DEV_DB_NAME=conduit_dev
DEV_DB_HOSTNAME=127.0.0.1
DEV_DB_DIALECT=postgres
DEV_DB_LOGGING=false

Then create the database. Tables are created automatically by sequelize.sync when the backend starts.

npm run sqlz -- db:create

Run

Playwright starts the app itself (npm run dev) unless it is already running on :3000/:3001.

npx playwright test                              # all tests, all 3 browsers
npx playwright test --project=chromium           # one browser
npx playwright test tests/e2e/negative.spec.js   # one file
npx playwright test -g TC09                      # one test case
npx playwright show-report                       # open HTML report
node scripts/summarize.js                        # pass/fail table per browser

Confirmed defects are marked with test.fail(). They count as expected failures, so the default run stays green. To see them as real failures (with screenshots, video and trace for the bug reports), run:

# bash
SHOW_BUGS=1 npx playwright test
# PowerShell
$env:SHOW_BUGS=1; npx playwright test

Env overrides: BASE_URL (default http://localhost:3000), API_URL (default http://localhost:3001/api).
